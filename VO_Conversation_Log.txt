C) `visual_odometry.py` (exact behavior)
--------------------------------------------------------------------
This is the VO math engine. It contains two classes:
1) `DepthProjector`
2) `VisualOdometryDepth`

C1) `DepthProjector` responsibilities
- Holds mode-specific intrinsics, extrinsics, depth scaling, and alignment settings.
- Converts raw MONO16 depth + pixel coordinates into 3D points in vehicle body frame.

C2) Mode-specific calibration tables
Virtual mode defaults include:
- RGB intrinsics (fx/fy/cx/cy) from your virtual FAQ table.
- Depth intrinsics from virtual table.
- `VIRTUAL_DEPTH_SCALE_UINT16 = 15707.0`.
- Virtual camera-to-body extrinsic transform (`VIRTUAL_T_CAM2BODY`).
- Virtual depth-to-color homography matrix (`VIRTUAL_ALIGNMENT_M`).

Physical mode defaults include:
- Calibrated RGB intrinsics (post calibration values).
- Calibrated depth intrinsics (post calibration values).
- `PHYSICAL_DEPTH_SCALE_UINT16 = 1000.0` placeholder currently in code.
- Physical camera-to-body transform (`PHYSICAL_T_CAM2BODY`) in meters.
- Physical depth->color 4x4 extrinsic transform (`PHYSICAL_T_DEPTH_TO_COLOR`) from calibration snapshot.
- Physical alignment model set to projective (not homography).

C3) Alignment model used by each mode
- Virtual: `alignment_model='homography'` via `warpPerspective`.
- Physical: `alignment_model='projective'` via depth->color 3D reprojection.

C4) Physical projective alignment details (`_align_depth_projective`)
For each valid depth pixel:
1. Backproject depth pixel to depth-camera 3D using depth intrinsics.
2. Transform depth-camera 3D point into color-camera frame using depth->color extrinsics.
3. Reproject into color image pixel coordinates using RGB intrinsics.
4. Rasterize with a z-buffer strategy (nearest point wins per color pixel).

This is depth-dependent alignment, not a single global 2D warp. That is why it is physically more correct for D435 geometry.

C5) 3D point generation for motion estimation (`pixels_to_3d_body`)
Given matched feature pixels:
- Samples aligned depth at those pixels.
- Backprojects to camera rays.
- Uses:
  - `K_rgb_inv` if alignment ON (depth now in color grid)
  - `K_depth_inv` if alignment OFF fallback
- Transforms to body frame with `R_cam2body, t_cam2body`.
- Returns Nx3 body-frame points and validity mask.

C6) `VisualOdometryDepth.update` algorithm
Per frame:
1. Optional undistortion.
2. ORB detect+compute on color image.
3. Align raw depth and convert to mode units.
4. Match current descriptors to previous with BFMatcher + Lowe ratio.
5. Backproject matched pixels (prev frame and current frame) to 3D body points.
6. Keep correspondences where both frames have valid depth.
7. Use only XY components (body-frame planar motion estimate) from those 3D points.
8. Estimate rigid transform with `_ransac_motion`:
   - 2-point random samples
   - SVD Procrustes solve
   - inlier test under residual threshold
   - refit on best inliers
9. Extract `(dx, dy, dpsi)` from best rigid transform.
10. Apply safety gates (`max_translation`, `max_rotation_deg`, `max_dt`).
11. Optional sign flip (`negate_deltas`) to convert feature-motion sign to vehicle-motion sign.
12. Accumulate pose in map frame via current heading.
13. Store diagnostics:
   - inlier count
   - confidence
   - inlier spread (from inlier pixel distribution)

Key point:
- Motion is not forced by Cartographer here. Translation increments come from camera feature/depth geometry and RANSAC/SVD.

Root cause identified in `qcar2_camera_bridge.cpp::connectStream()`.
`qcomm_connect` with `non_blocking=true` returns `-QERR_WOULD_BLOCK`
to indicate the TCP connection is in progress — that is the EXPECTED
behavior per the Quanser API documentation. The caller is required
to then invoke `qcomm_poll(conn, timeout, QCOMM_POLL_CONNECT)` to
wait for the connection to complete. The bridge's earlier connect
logic treated ANY negative return as a fatal failure and returned
before setting `conn_open_=true`, so the worker thread kept calling
`connectStream()` every 250 ms. Each call queued a fresh half-open
TCP connection at the runtime and abandoned it before completing
the handshake. Result: the kernel's accept-queue at the runtime
grew (Recv-Q = 19 -> 33) while the runtime never received a fully
established client.

Fix applied:
- `connectStream()` now branches explicitly:
    if (r < 0 && r != -QERR_WOULD_BLOCK) -> real failure, abort
    else if (r == -QERR_WOULD_BLOCK) -> connection in progress;
        set conn_open_=true and enter the existing 2 s poll-for-
        CONNECT loop
    else (r == 0) -> connection completed synchronously
- The poll-for-CONNECT loop was already present in the function but
  was unreachable behind the early return. It now runs correctly.
- Added an in-source comment block explaining the non-blocking
  protocol so this never gets re-broken.
