You’re thinking in exactly the right direction. Here’s the clean way to do this without risking the car.

Core VO Goal (and one critical rule)
1. Goal stays: camera-based pose as an independent redundancy check for Cartographer.
2. Critical rule: do not directly use Cartographer yaw inside VO residual decisions, or we lose independence.
3. Better approach: if we add IMU, use raw IMU as a separate aid (VIO-assist), and keep a pure-camera VO channel for fault-check truth.

About yaw/theta, IMU, quaternions
1. Theta was weak in sim.
2. Quaternions are good representation, but they do not create new yaw information.
3. Practical design later: VO_pure and VO_assist.

What already matches now
1. Hardcoded 640x480 physical intrinsics match live D435 readout.
2. Depth units from camera are 0.001 m (1000-scale).
3. Missing in active runtime path: automatic fetch/use of color-depth extrinsics + depth scale.

Why rgbd matters
1. Not all launch paths start rgbd.
2. qcar2_launch.py has rgbd commented out.
3. qcar2_manual_drive_launch.py has rgbd active.

Why rgbd_get_meters_probe can fail in virtual but still help on physical
1. It uses video3d_frame_get_meters(...).
2. QLabs virtual path is not always equivalent to physical metric path.
3. Probe can conflict with normal rgbd if both open stream.
4. On physical D435 it is hardware-backed and useful.

Physical test flow
1. Pre-check logs: rs-enumerate-devices -c and -o.
2. Controlled stack: manual drive + cartographer + vo_node physical.
3. Monitor /vo/fault_status first.
