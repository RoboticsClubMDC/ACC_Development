*** QoS GOTCHA (read before any playback) ***
camera_bridge publishes /camera/* as BEST EFFORT (sensor QoS), and
a bag of it replays Best Effort. RTAB-Map's INSTALLED launch (pre
2026-05-21) subscribes RELIABLE -> incompatible -> ZERO frames
reach RTAB-Map -> empty rtabmap_viz GUI + ~90 KB empty db. Symptom
in the bag-play terminal: "requesting incompatible QoS. No messages
will be sent ... RELIABILITY_QOS_POLICY".

Two ways to fix:
  (1) NO REBUILD (works with the currently installed launch): force
      the bag PLAYER to republish /camera/* as Reliable using the
      override file ~/vo_rtab_bags/qos_reliable.yaml. Add this flag
      to every `ros2 bag play` below:
        --qos-profile-overrides-path /home/nvidia/vo_rtab_bags/qos_reliable.yaml
  (2) AFTER REBUILD: qcar2_rtabmap_launch.py now defaults qos:=2
      (Best Effort), so RTAB-Map matches the bag and the override
      file is NO LONGER needed. Rebuild qcar2_nodes (Section 0.6)
      to switch to this path.
The commands below include the (1) override so they work today.
qos_reliable.yaml contents (recreate if missing): /camera/* ->
reliable+volatile, /tf_static -> reliable+transient_local.

7.7) Cartographer-jump investigation
----------------------------------------------------
User observed unphysical x-jumps in /vo/odometry (0.12 m in 200 ms
at a commanded 0.1 m/s, ~6x actual velocity) and similar magnitude
jumps in the Cartographer pose. NOTE: there is no /odom topic;
Cartographer's pose is captured in the bag as /tf (map->base_link)
and, conveniently, as the scalars /vo/cart_x, /vo/cart_y,
/vo/cart_psi (vo_node republishes the TF lookup). The bag captures
all of these, so this is a pure offline analysis — no car needed.

Easiest path: hand the bag to Claude. It can read the sqlite3 bag
directly (no live playback, no temp files) and plot:
  - /vo/vo_x   vs /vo/cart_x   (VO x vs Cartographer x)
  - /vo/vo_y   vs /vo/cart_y
  - /vo/vo_psi_shadow vs /vo/cart_psi  (camera-only yaw vs the
    force_cart_yaw-applied yaw)
and flag synchronized jumps through the curve segment.

The point of capturing both: determine whether the jumps are
VO-only (bad-match / depth glitch), Cartographer-only (its pose
estimate jumping), or synchronized (a shared timing/source issue) —
which directly informs EKF weighting when robot_localization is
wired.
